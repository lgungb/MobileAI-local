# 05 · 数据与存储（现状事实）

> 本文只记录**代码现在实际是怎么存数据的**，以及历史上反复出问题的地方。
> 不写"应该怎么设计"（那在 `06_重构方案.md`）。
> 改动任何读写逻辑前，先读完本文第 3、5 节。

---

## 1. 存储总览：5 个 DataStore，全是裸配置

全部由 `di/AppModule.kt` 用 `DataStoreFactory.create(serializer, produceFile)` 直接创建，
**没有任何 `corruptionHandler`，也没有 `migrations`**（`:96`、`:109`、`:122`、`:135`、`:148`）。

| 文件（`files/datastore/`） | 类型 | 承载内容 | 写入频率 | 风险 |
| --- | --- | --- | --- | --- |
| `settings.pb` | `Settings` | 主题、导入模型清单、API 多套配置、语音、定时任务、本地服务、默认模型、每模型后端 | **高**（说话/改设置都写） | 高 |
| `user_data.pb` | `UserData` | **全部会话 + 全部消息**、会话记录（特调）、密钥、MCP 授权、Prompt Lab 自定义项 | **最高**（每轮对话结束写） | **最高** |
| `skills.pb` | `Skills` | 技能列表 + 勾选状态 | 中 | 中 |
| `benchmark_results.pb` | `BenchmarkResults` | 跑分记录 | 低 | 低 |
| `cutouts.pb` | `CutoutCollection` | 便签/剪贴画（上游遗留） | 极低 | 低 |

**关键事实 ①：`user_data.pb` 是一个巨型单文件。**
`UserData.chat_sessions` 是 `repeated ChatSessionProto`（`settings.proto:216`），
每个 `ChatSessionProto` 内含 `repeated ChatMessageProto`（`chat_history.proto:78`）。
也就是说——**所有会话、所有消息、所有特调记录，装在同一份 proto 里**。

写一条消息的实际动作（`ChatViewModel.kt:564-592`）：

```
updateData {          // 读出整个 user_data.pb
  clearChatSessions() // 清空全部会话
  addAllChatSessions(全量会话)  // 重新加回全部会话（含全部历史消息）
  clearConversationProfiles() / addAllConversationProfiles(全量记录)
}                     // 整体序列化 → 原子替换整个文件
```

⟹ **单次写入成本 = O(全部会话 + 全部消息 + 全部记录)**。
会话越用越多，每次保存越慢，写盘窗口越长，被系统杀掉/断电导致写入中断的概率越高。

**关键事实 ②：没有损坏兜底。**
`settings.pb` 或 `user_data.pb` 一旦解析失败（写中断、磁盘满、字段号冲突、旧版本残留），
`DataStore.data` 会持续抛 `CorruptionException`。因为没有 `corruptionHandler`，
App **每次启动都会崩**，且无法自愈——只能清数据。
表现就是 `CrashDisplayActivity` 的"黑屏 + 白色英文堆栈"。

## 2. 谁在写 Settings

5 个仓库共用同一个 `DataStore<Settings>`，各自 `map` 出自己那一段：

| 仓库 | 负责字段 |
| --- | --- |
| `ApiProviderRepository` | `api_providers` / `active_api_provider_id` / `use_remote_api` |
| `VoiceSettingsRepository` | `voice_engine` / `voice_rate` / `voice_pitch` / `voice_role` |
| `TimedTaskRepository` | `timed_tasks` |
| `LocalServerRepository` | `local_server` |
| `DefaultDataStoreRepository` | 其余全部（主题、导入模型、默认模型、模型后端、输入历史、Skill 等） |

这一层**本身的设计是对的**（一个 store 管一类偏好），问题在 `DefaultDataStoreRepository` 的实现方式，见下节。

## 3. ⚠️ 三个已知的写入缺陷

### 3.1 `DefaultDataStoreRepository` 全篇 `runBlocking`（84 处）

`data/DataStoreRepository.kt` 里每个方法都是同步签名 + `runBlocking { dataStore.updateData {...} }`。
接口注释里还留着上游的 `TODO(b/423700720): Change to async (suspend) functions`（`:34`）。

**危害**：调用方如果在主线程（`ViewModel.init`、Compose 组合期、点击回调）调用，
主线程会同步等待「读文件 → 解析整份 proto → 修改 → 序列化 → 落盘」。
`settings.pb` 越大（定时任务、API 配置、导入模型越多），阻塞越久。

已知的主线程调用点（`ui/modelmanager/ModelManagerViewModel.kt`）：

| 行 | 调用 | 时机 |
| --- | --- | --- |
| `:570` / `:987` | `readImportedModels()` | 导入 / 删除模型 |
| `:674` | `readModelAccelerator(model.name)` | 每次初始化模型 |
| `:830` `:843` `:853` `:859` | `saveTextInputHistory()` | 每次发消息 |
| `:1437` | `readImportedModels()` | 启动时扫描已下载模型 |
| `:1477` / `:1487` | `readTextInputHistory()` / `readDefaultModelId()` | ViewModel 初始化 |
| `:400` `:409` | `saveDefaultModelId` / `saveModelAccelerator` | 模型页操作 |

`skills/SkillManager.kt:99` `:133` `:933` `:935` 也是同步读写。

**症状**：进入模型页/设置页卡顿、发消息偶发掉帧、ANR、启动后默认模型/后端读到旧值。

### 3.2 「读快照 → 改 → 整体覆盖」会丢更新

正确写法是**在 `updateData` 的闭包里读 `proto` 再改**（`TimedTaskRepository.kt:103`、
`LocalServerRepository.kt:63`、`ConversationProfileRepository.kt:154` 都是对的）。

但下列位置是**先 `read...()` 拿快照，改完再 `save...(整个列表)` 覆盖**：

- `ModelManagerViewModel.kt:570-575`（导入模型）
- `ModelManagerViewModel.kt:987-994`（删除模型）
- `SkillManager.kt:933-935`（技能勾选状态）

一旦两次操作交叉（例如导入模型的协程还没写完，用户又删了一个），
后写的那次会**用旧快照覆盖掉前一次的结果**。
症状：导入的模型"自己消失"、技能勾选"自己变回去"。

### 3.3 `saveAccessTokenData` 跨两个 store，非原子（`DataStoreRepository.kt:230`）

先写 `settings.pb` 清空、再写 `user_data.pb` 赋值。中间失败会留下半完成状态。
目前该路径基本已弃用（`access_token_data` 在 proto 里标了 `deprecated`），但代码还在。

## 4. 其它已确认的坑

### 4.1 采样参数键名：读用 `label`，存用 `id`

| 侧 | 键 | 例 | 位置 |
| --- | --- | --- | --- |
| 运行时读 `model.configValues` | `ConfigKey.label` | `TopK` | `data/Model.kt:408` |
| 记录持久化 `ConversationProfile.configValues` | `ConfigKey.id` | `topk` | `conversation/ConversationProfile.kt:102` |

直接把记录的 map 塞进 `model.configValues` **静默失效**（读不到、不报错）。
必须走 `LlmChatViewModel` 的 `PROFILE_CONFIG_KEYS` 白名单 + id→label 映射 + 类型转换。

### 4.2 两个 store 都 `import conversation_profile.proto`

`settings.proto:21` import 了它，`UserData.conversation_profiles` 用到（`:225`）。
改 `conversation_profile.proto` 会同时影响两个 store，**必须只用新字段号，不允许复用/改类型**。

### 4.3 会话与记录是 1:N，靠 `ChatSessionProto.profile_id` 关联

删除记录要级联删会话（`ConversationProfileRepository.kt:271-277`）+ 清理 `cacheDir` 的
`img_` / `audio_` 媒体文件。漏了后者就是"删了对话但存储没释放"。

### 4.4 会话只在「本轮生成结束」时落盘

`ChatView.kt:425` `LaunchedEffect(uiState.inProgress)` → 生成结束时 `saveSession` 一次。
所以**生成过程中杀进程，这一轮回复会丢**。这是当前设计的事实，不是 bug，但用户会当成 bug。

## 5. 故障症状 → 大概率根因（排障用）

| 你看到的现象 | 先去查 |
| --- | --- |
| 启动即崩，黑屏+白色堆栈，清数据后正常 | `*.pb` 损坏 + 无 `corruptionHandler`（§1 事实②） |
| 设置改了没生效 / 重启后回退 | 主线程 `runBlocking` 读到旧快照（§3.1）；或快照覆盖（§3.2） |
| 导入的模型 / 勾选的技能自己消失 | 快照覆盖丢更新（§3.2） |
| 对话越多越卡，发一条消息要顿一下 | `user_data.pb` 全量重写（§1 事实①） |
| 采样参数调了没用 | `label`/`id` 键名不一致（§4.1） |
| 切对话后推理后端串了 / 卡死 / 闪退 | `model_accelerators` 未按模型隔离（已在 `220b21a` 修复，回归时先看这里） |
| 删了对话，存储没变小 | 媒体缓存 `cacheDir/img_*`、`audio_*` 没清（§4.3） |

## 6. 改数据层时必须遵守的不变量

1. **写只在 `updateData` 闭包里改**，禁止"先读快照、后整体覆盖"。
2. **proto 只加新字段号**，永不改类型、永不复用已删字段号。
3. **新增同步接口一律禁止**——新代码只能写 `suspend`，不许再往 `DefaultDataStoreRepository` 加 `runBlocking` 方法。
4. **UI 层不直接持有 `DataStore`**，只经仓库。目前 `ChatViewModel.kt:628` 有直接 `.data.first()` 的旁路。
5. **迁移必须幂等**，参考 `ConversationProfileRepository.migrateLegacySessionsIfNeeded`（靠标记位只跑一次，允许重入）。
