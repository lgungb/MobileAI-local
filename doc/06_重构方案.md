# 06 · 重构方案：只换数据层，不重写 App

> 结论先行：**这个 App 不需要重写，需要"换地基"。**
> 重写整个 App 要重踩 NPU 推理、离线 TTS、定时任务、本地 API Server 四类已经踩平的坑；
> 而 80% 的 bug 集中在一个很小的范围——**数据与设置的持久化层**。
> 把这一层换掉，收益接近重写，代价大约是重写的 1/10。

---

## 1. 为什么不全量重构（对比）

| 方案 | 代价 | 风险 | 能解决的 bug | 结论 |
| --- | --- | --- | --- | --- |
| A. 全量重写（新工程） | 极大（几万行 Kotlin/Compose） | 极高：NPU/TTS/闹钟/SAF 全要重调 | 全部 | ❌ 不建议 |
| B. **换数据层（本文方案）** | 中（约 1500~2000 行改动，集中在 `data/`） | 中：迁移期要保证不丢老数据 | 数据类 + 设置类 bug 的绝大多数 | ✅ **推荐** |
| C. 只打补丁（继续局部修） | 低 | 低 | 单个现象，治不了系统性 | ⚠️ 只能止血 |

**支撑判断的三个事实**（详见 `05_数据与存储.md`）：

1. 所有会话/消息装在一份 `user_data.pb` 里，每次保存全量重写 ⟹ 越用越慢、写盘窗口越长、越容易写坏。
2. 5 个 DataStore 全是裸 `DataStoreFactory.create()`，无 `corruptionHandler`、无迁移 ⟹ 文件一坏就无限崩溃，只能清数据。
3. `DefaultDataStoreRepository` 84 处 `runBlocking` + 多处"读快照后整体覆盖" ⟹ 主线程阻塞、设置丢更新。

这三条都是**结构性**的，靠在业务代码里加 try-catch 修不掉。

## 2. 目标结构

```
data/
├── store/
│   ├── StoreFactory.kt        # 唯一的 DataStore 创建入口（含损坏恢复 + 备份）
│   ├── CorruptionRecovery.kt  # 坏文件先备份到 files/backup/，再重置，绝不静默丢
│   └── SchemaVersion.kt       # 版本号 + 迁移链（顺序执行、幂等）
├── settings/
│   └── SettingsRepository.kt  # 唯一入口；全 suspend；对外只暴露 StateFlow<AppSettings>
├── conversation/
│   ├── SessionFileStore.kt    # 一个会话一个文件：sessions/<sessionId>.pb
│   ├── SessionIndexStore.kt   # 轻量索引（id/标题/时间/profileId/预览/消息数）
│   └── ConversationProfileRepository.kt  # 保留，改为走新 store
└── ...
```

### 2.1 会话文件化（最关键的一步）

| | 现在 | 改造后 |
| --- | --- | --- |
| 存储 | 1 份 `user_data.pb` 装全部会话 | 1 会话 1 文件 `sessions/<id>.pb` + 1 份轻量索引 |
| 打开列表 | 反序列化全部消息 | 只读索引 |
| 保存一条消息 | 全量重写所有会话 | 只写当前会话文件 |
| 单会话损坏 | **全部数据一起挂** | 只有那一条打不开，其余正常 |
| 复杂度 | O(总会话×总消息) | O(单会话消息数) |

索引文件只放列表要用的字段（几十字节/条），不做全量消息读取。

**兼容迁移**：首启检测 `UserData.chat_sessions` 非空且迁移标记未置位 → 逐个拆成文件 → 写索引 →
清空 `chat_sessions`（**字段号保留，不删除定义**）→ 置迁移标记。全程幂等，允许中断重入。

### 2.2 损坏恢复（防"清数据才能用"）

```kotlin
// data/store/StoreFactory.kt（示意）
inline fun <reified T : MessageLite> createStore(
  context: Context, fileName: String, serializer: Serializer<T>, default: () -> T,
): DataStore<T> = DataStoreFactory.create(
  serializer = serializer,
  // 坏文件先另存一份，再返回默认值 —— 让 App 能启动，且数据可捞
  corruptionHandler = BackupAndReplaceHandler(fileName) { default() },
  produceFile = { context.dataStoreFile(fileName) },
)
```

备份落在 `files/backup/<fileName>.<时间戳>.corrupt`，在「系统 → 文件管理」里能看到，
或加一个「导出诊断数据」按钮把备份打出来。

### 2.3 写入纪律（三条硬规则）

1. 仓库对外**只有 `suspend`**，内部**只在 `updateData` 闭包里读改**——杜绝快照覆盖。
2. 所有写操作经一个 `Mutex` 串行（同一 store 内），避免交叉覆盖。
3. UI 只读 `StateFlow`，不在组合期调同步 IO。

### P0-5 的实现要点（后续改动别踩回去）

- 引擎侧只认「初始化时传入的 systemInstruction」，发消息的 `AgentRequest` **不带提示词**（`LlmChatViewModel.generateResponse` 本地分支）。
- 因此记录级提示词必须通过两条路径生效：
  1. 模型还没初始化 → 写 `Model.pendingSystemInstruction`，`initializeModel` 优先采用；
  2. 模型已保活 → `resetSession(clearHistory = false, systemInstruction = 记录提示词)`，只重置 KV cache，不重载权重。
- `Model.appliedSystemInstruction` 用于比对"引擎当前到底用的什么"，避免每次进页面都重置。
- **不要**为了省事在 `bindProfile` 里只改 `_uiSystemPrompt` —— 那正是串台的成因（界面对了、引擎没动）。

#### P1 进度说明（读这段再动手）

**已完成：读写主路径已切到文件层。** 现在的数据流向：

- **写**：`ChatViewModel.saveSession` → `SessionFileStore.writeSession` → 只写这一条会话的
  `.pb`（`.tmp` + rename 原子替换）+ 更新 `index.tsv` 里对应的那一行。
  `UserData.chat_sessions` **不再写入**，降级为回退快照。
  （写文件失败时会自动退回旧的整份写入，宁可慢也不丢。）
- **列表读**：`SessionFileStore.indexState`（内存镜像）→ `toLiteProto()` 只带元数据。
  历史侧边栏滚动**不解析任何 `.pb`**。
- **详情读**：点开某条时才 `readSession(sessionId)` 读那一个文件；读不到回退旧字段。
- **删除**：会话文件 + 索引 + 旧字段一起删；删特调记录时会级联删会话文件
  （`ConversationProfileRepository.collectOwnedSessionIds` 已并入索引来源）。
- **导出**：`readAllSessions()` 按索引逐条读全文（IO 线程），不再依赖列表自带正文。

**一次性切换**：`SessionMigrator.cutoverIfNeeded()`，由 `GalleryApplication` 启动时调用。
顺序固定，改动前务必读该方法的 KDoc：

1. 清掉迁移标记并**重跑迁移**（补齐上一版只写在旧字段里的会话）；
2. 迁移有失败 → **直接中止**，保持旧路径，下次启动重试；
3. 用旧字段的 id 集合 `pruneOrphans()` 清掉「已删但文件还在」的孤儿，防止切换后复活；
4. 落 `secrets["session_file_cutover_v1"] = done`，保证只跑一次。

> ⚠️ **这一步不可逆**：切换之后回退到旧版本 APK，会看不到切换后新建的会话。
> 回退手段是把 `files/migration_backup/user_data-*.pb` 覆盖回 `files/datastore/user_data.pb`。

**剩余**：P1-5（导出全部会话为 zip 的备份/恢复入口）。

## 4. 不要做的事（明确排除，避免越改越大）

- ❌ **不引入 Room**。当前数据量是"几十个会话"，文件化就够；Room 会带来 migration、连接池、线程模型一整套新问题。等要做全文搜索/分页再评估。
- ❌ **不做多模块拆分**。收益在编译速度，不在稳定性，现在拆只会增加改动面。
- ❌ **不重写 UI**。UI 是能用的资产，改数据层时**保持 UI 契约不变**是关键约束。
- ❌ **不动 `conversation_profile.proto` 已有字段号**。两个 store 都 import 它，动错一个就双崩。
- ❌ **不引入新的序列化格式**（如 JSON 替换 proto）。迁移成本全部落在用户数据上，收益低。

## 5. 风险与回滚

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 迁移中途被杀 | 部分会话未拆文件 | 迁移器幂等（按 sessionId 判断已存在则跳过）+ 保留原 `chat_sessions` 直到全部成功 |
| 迁移后用户不认账（会话丢） | 严重 | 迁移前先把 `user_data.pb` 复制一份到 `files/backup/pre_migrate.pb`；提供"从备份恢复"入口 |
| 备份文件堆积占空间 | 中级 | 备份最多保留 3 份，超出按时间删最旧 |
| 改数据层牵连 UI 编译错误 | 中 | 分批提交，每批可构建；先把旧 API 标 `@Deprecated` 保留一版 |

**回滚方式**：迁移只"读旧写新"，不删旧字段内容（只清空 `chat_sessions` 前先备份）。
真要回滚，把备份的 `user_data.pb` 覆盖回去 = 回到旧版本状态。

## 7. 怎么验证"确实变好了"（不看代码，看行为）

1. **压力场景**：造 100 条会话 × 每条 50 轮，然后连续发 30 条消息。
   - 现状：明显卡顿、偶发 ANR
   - 目标：无卡顿，写盘耗时稳定在 20ms 内
2. **损坏场景**：手动截断 `user_data.pb` 一半 → 重启。
   - 现状：无限崩溃
   - 目标：正常启动 + 生成 `.corrupt` 备份
3. **并发场景**：一边导入模型一边删技能 → 重启核对。
   - 现状：一方丢失
   - 目标：两边都在
4. **升级场景**：装旧版（1.0.36）造数据 → 覆盖安装新版 → 会话列表逐条点开。
   - 目标：标题、消息、特调参数全部一致
