## 〇、本轮已修复（2026-11-01）

### 本地 API 服务绑端口失败导致闪退（SocketException: Permission denied）【已修复】
- **现象**：Android 17（API 37）真机上，点设置里的「本地 API 服务」开关后 App 直接闪退。
  崩溃堆栈为 `sun.nio.ch.Net.bind0` 抛 `java.net.SocketException: Permission denied`，
  发生在 `DefaultDispatcher-worker-6`（Ktor CIO 引擎的异步 accept 协程）。
- **根因**：`LocalApiServer.start()` 用 `embeddedServer(CIO, ...).start(wait = false)` 异步启动，
  真正的端口绑定发生在 Ktor 自己的后台线程里，`SocketException` **绕过了外层 try-catch**，
  冒泡到全局崩溃处理器 → 杀进程闪退。且 `LocalServerService` 在 App 启动时就会自动 start
  （若上次开关未关），导致「重启也闪退」。
- **修复**（commit `a06686e`）：① `start()` 前用 JDK `ServerSocket` 做**同步端口预检**，
  bind 失败就不启动 Ktor、绝不崩溃；② 特权端口下限从 1 提升到 1024（`effectivePort` + `canBind` 双保险）；
  ③ `LocalServerService.initialize` 的 collect 与启停全程 try-catch 兜底。
- **残余**：Android 上跑 Ktor CIO 服务器本身非官方支持，此功能仍是「半成品」，
  建议后续评估是否值得保留（见下方第 2、3、12 条）。

## 一、Bug（功能性缺陷）

### 1. 本地 API Server 与对话页共享同一个 AgentRuntimeExecutor 单例，推理会互相覆盖
- **文件/位置**：`data/server/LocalApiServer.kt` `runInference()`（约 :430）
- **类型**：Bug · 并发 / 状态污染
- **说明**：`LocalApiServer.runInference` 直接调用注入的 `AgentRuntimeExecutor`（Hilt 单例），
  而该 executor 内部用 `AtomicReference<ActiveSession>` 保存「当前会话」。当本地 API Server
  收到外部请求执行 `initialize()` 时，会把 `activeSession` 覆盖成「local_api_server」任务；
  此时若用户正在对话页和本地模型对话，其会话会被悄悄顶掉，反之亦然。两者共用同一个模型
  runtime 实例，极易串扰。
- **建议**：为 LocalApiServer 单独注入一个 executor 实例（`@Named("local_server")` 限定），
  或至少在 `initialize` 前检测并拒绝「已有其它会话占用模型」的请求，返回 503。

### 2. LocalApiServer 每次配置变化都 stop + 重启整个服务器（含端口输入每个字符）
- **文件/位置**：`data/server/LocalApiServer.kt` `start()`（:110）、`ui/home/LocalServerSection.kt`
  端口输入 `onValueChange`（:87）
- **类型**：Bug · 资源抖动
- **说明**：`LocalServerService.initialize` 订阅 `repository.settings`，任何字段变化都会触发
  `apiServer.start()` → 先 `stop()` 再 `embeddedServer(...)` 重新起。而设置页端口输入框
  **每敲一个数字**就 `viewModel.setPort(it)` → `repository.update` → settings 流触发 →
  服务器重启一次。连续输入端口号会高频重建 Ktor server，浪费资源且可能短暂不可用。
- **建议**：端口 / Token 等字段改动不立即重启，改为「失焦或显式保存按钮」才生效；
  或对 settings 做去抖（debounce），相同配置不重启。

### 3. LocalServerViewModel.isRunning 用每秒轮询的无限 flow
- **文件/位置**：`ui/home/LocalServerViewModel.kt` `isRunning`（:50）
- **类型**：Bug（轻度）· 资源浪费
- **说明**：`isRunning` 用 `flow { while(true) { emit(apiServer.isRunning); delay(1000) } }`
  每秒轮询一次 `@Volatile` 字段。UI 只要订阅就有一个常驻计时器在跑，浪费且不实时。
- **建议**：改成 `MutableStateFlow<Boolean>`，由 `LocalApiServer.start/stop` 直接更新，
  订阅侧零轮询。

### 4. 全局未捕获异常处理器在主线程 sleep 阻塞
- **文件/位置**：`GalleryApplication.kt` `onCreate()` 的 `Thread.setDefaultUncaughtExceptionHandler`（:46）
- **类型**：Bug · 错误处理
- **说明**：崩溃处理器里 `Thread.sleep(500)` 后再 `killProcess`。若崩溃发生在主线程，
  这 500ms 会阻塞主线程，且 `CrashDisplayActivity.start` 依赖主线程继续调度才能拉起。
  极端情况下崩溃页可能起不来，直接卡住。
- **建议**：去掉 sleep，改用 `Process.killProcess` + 一个独立线程延时兜底；或改为
  `Handler(Looper.getMainLooper()).postDelayed` 延时启动崩溃页再杀进程。

## 二、代码质量缺陷 / 可优化代码

### 5. ApiSecretCipher.obtainKey() 每次加解密都重新打开 KeyStore 并可能重复生成密钥
- **文件/位置**：`data/api/ApiSecretCipher.kt` `obtainKey()`（:38）
- **类型**：代码质量 · 性能
- **说明**：`obtainKey()` 每次 `encrypt/decrypt` 都执行 `KeyStore.getInstance().load(null)` +
  `getEntry`（Keystore 硬件 I/O）。`ApiProviderRepository` 的 `configs`/`activeConfig` 两个 Flow
  每次 DataStore 刷新都会解密所有配置，等于重复打开 KeyStore。本次已用「解密缓存 + flowOn(IO)」
  缓解了主线程卡死，但根因（obtainKey 无缓存）仍建议修复。
- **建议**：密钥 `SecretKey` 用 `@Volatile` 字段缓存一次，之后复用，避免重复 `load` / `generateKey`。

### 6. NewConversationDialog 硬编码中文字符串，未走 strings.xml
- **文件/位置**：`ui/conversation/NewConversationDialog.kt`（全文文案）、
  `ui/conversation/SaveProfileDialog.kt`（既有）
- **类型**：代码质量 · 规范一致性
- **说明**：新弹窗的标题、按钮、提示文案全部硬编码中文，未按项目「values + values-zh 双语资源
  对齐」的既有规范放入 strings.xml。项目其余界面基本都走 `stringResource`。
- **建议**：抽出 `@StringRes` 资源（至少 values-zh），与 `SaveProfileDialog` 一并整改。

### 7. PresetPrompts 提示词库为纯 Kotlin 静态列表，不易运营维护
- **文件/位置**：`data/conversation/PresetPrompt.kt`
- **类型**：代码质量 · 可维护性
- **说明**：几十条提示词硬编码在 Kotlin 对象里。将来要增删改、做远程下发或多语言，得改代码重编。
- **建议**：短期可接受；若提示词要产品化，可迁到 `assets/prompt_presets.json` 启动加载，
  支持远程更新与多语言。

## 三、结构设计问题

### 8. 本地 API Server 的模型桥接依赖「组合期挂载」的 modelProvider，生命周期脆弱
- **文件/位置**：`data/server/LocalApiServer.kt` `modelProvider`（:96）、`GalleryApp.kt` 挂载处
- **类型**：结构设计 · 生命周期
- **说明**：`modelProvider: (() -> Model?)?` 是 `@Volatile` 可变字段，由组合层在 Composition 期挂载。
  若 Activity 重建 / 组合销毁后忘记清理，会持有过期的 Model 引用；反之未挂载时本地 API 永远 503。
  与 `TaskAiInvoker.modelProvider` 是同样的脆弱模式（两处重复）。
- **建议**：抽一个 `LocalModelProviderHolder` 单例统一管理挂载/解绑，LocalApiServer 与
  TaskAiInvoker 都从它取，消除重复与悬空引用风险。

### 9. 会话「进入」与「新建」对模型选择的语义不一致，散落在导航层
- **文件/位置**：`ui/navigation/GalleryNavGraph.kt` `openProfile`（N7 强制全局默认模型）vs
  `startNewConversation`（用所选模型）
- **类型**：结构设计 · 语义一致性
- **说明**：点旧记录进入时强制用全局默认模型（profile 只提供提示词/参数，不绑定模型），
  而新建时用用户选的模型。两条路径对「模型从哪来」的口径不统一，且都手写在导航层，
  后续维护容易踩坑。
- **建议**：把「解析进入会话用哪个模型」收敛成一个函数并写清规则（何时用全局默认、何时用记录模型、
  何时用所选模型），导航层只调用不重复实现。

## 四、非功能性问题（性能 / 内存 / 错误处理）

### 10. ChatView 模型初始化 LaunchedEffect 以整个下载状态对象为 key，易频繁重启
- **文件/位置**：`ui/common/chat/ChatView.kt`（:448）`LaunchedEffect(curDownloadStatus, selectedModel.name)`
- **类型**：非功能 · 性能
- **说明**：key 之一 `curDownloadStatus` 是 `ModelDownloadStatus?`（data class）。`modelDownloadStatus`
  是 `_uiState` 里的 map，任何一次 `setDownloadStatus`（含下载进度每帧更新）都会替换整个 map，
  使 `curDownloadStatus` 引用变化，LaunchedEffect 重启并再次调用 `initializeModel`。
  虽然 `initializeModel` 有「已初始化跳过」兜底，但每次重启仍有一次空转 + 日志 + 状态判断开销。
- **建议**：key 收敛为稳定字段，例如 `LaunchedEffect(selectedModel.name, curDownloadStatus?.status)`，
  只在「模型名」或「下载状态枚举」变化时才重启。

### 11. 大量 Log.d/Log.w 散布在热路径，未分级收敛
- **文件/位置**：`ui/navigation/GalleryNavGraph.kt`、`ui/common/chat/ChatView.kt`、`ModelManagerViewModel.kt` 等
- **类型**：非功能 · 性能 / 可读性
- **说明**：模型初始化、切换、导航等高频路径有大量 `Log.d`（如 `Initializing model ... from ChatView
  launched effect`），release 构建下虽可能被 R8 裁剪，但调试信息噪音大、难以定位关键错误。
- **建议**：统一走项目已有的 `DebugLog`，分 T 级（Trace）/ I / W / E，热路径用 Trace 级默认关闭。

### 12. LocalApiServer 推理无并发限制与排队机制
- **文件/位置**：`data/server/LocalApiServer.kt` `handleChatCompletions`（:265）
- **类型**：非功能 · 健壮性
- **说明**：每个 HTTP 请求直接 `runInference`，无信号量 / 队列限制。局域网多客户端同时调用会并发
  抢占同一个模型 runtime（端侧模型通常不支持并发推理），可能 OOM 或崩溃。
- **建议**：加 `Mutex` / `Semaphore(1)` 串行化推理，超出时返回 429「模型忙，请稍后」。

## 五、规范性 / 一致性问题

### 13. 版本号与提交的对应关系需人工维护，易漏
- **文件/位置**：`app/build.gradle.kts` `versionCode` / `versionName`
- **类型**：规范性
- **说明**：约定「每提交 versionCode +1、versionName 末位 +1」，但靠人工记得改，漏改会导致
  多提交共用一个版本号，APK 无法区分。
- **建议**：可考虑在 CI / 提交钩子里校验「versionCode 是否已比上一个 release 提交 +1」；
  或把版本号从 git tag 推导。

### 14. ~~新建对话弹窗云端虚拟模型被误判为「未下载」不可选~~ 【已修复 2026-11-01】
- **文件/位置**：`ui/navigation/GalleryNavGraph.kt` 新建弹窗 `availableModels` 排序与 `isDownloaded`
- **类型**：规范性 · 边界
- **说明**：模型列表排序与「是否默认」都用 `model.name` 字符串比较；云端虚拟模型
  （`CLOUD_MODEL_NAME = "encourage-cloud-api"`）没有下载状态，`isDownloaded` 恒为 false，
  会被排到最后且显示「未下载」、不可选。若用户已配置外部 API，理应可选云端模型。
- **修复**：新增 `isReady(model)` 判断——已下载（SUCCEEDED）、AICore 运行时、云端虚拟模型
  三种情况均视为「就绪可选」，排序与可点选逻辑统一用它。
